### What Hermes ALREADY does for multi-model
This is the honest baseline — Airlangga does not start from zero here:
1. **One active model per session, switchable mid-session** (`/model`, `session_mutation_model.py`), with the switch persisted per session.
2. **Delegated children can run a different model/provider** than the parent (`delegation.model` / `delegation.provider`, §3).
3. **Fallback chains:** `delegation.fallback_providers` for children; `fallback_model` param on `AIAgent`; provider-level fallback/cooldown in the credential pool.
4. **Mixture-of-Agents per turn:** `agent/moa_loop.py` (+ `moa_alternation.py`, `moa_trace.py`) — "/moa turns": the slash command marks one user turn as MoA-enabled; "the normal agent loop still owns tool calling and turn termination, while this module gathers reference-model context before each model iteration" (module docstring). Reference slots have their own model/reasoning config and accounting (`_slot_reasoning_config`, `_aggregator_reasoning_config`, `_RefAccounting`). This is multi-model *consultation inside one turn*, not a team.
5. **Auxiliary models:** `agent/auxiliary_client.py` (`call_llm`) + `agent/auxiliary_*.py` (~20 files: task config, structured output, reasoning floor, rate-limit backoff, key rotation, health, hooks) — title generation, compression summaries, vision, embeddings and similar sub-tasks can run on a different/cheaper model than the main turn.
6. **API-server model routing** (above) and **cron job model pinning** (`cron/jobs_model_pin.py`, `scheduler.py: _resolve_job_reasoning_config`).
7. **What it does NOT have:** no persistent roster of named members each with their own pinned provider/model/identity; no per-member credential isolation (children inherit or take one global override); no team-level shared memory or decision protocol; no "Main Brain vs Team Brain" hierarchy — there is exactly one brain per session, and children are its tools.

## 3. Delegation / teams — what exists today and why it is NOT a persistent team

### The delegation tool
- Tool name: `delegate_task` (defined via `agent/delegation_provider.py`, implemented in `tools/async_delegation.py`, 1,594 lines). `delegate_task(background=true)` runs children asynchronously; the registry behind it is SQLite-backed and durable (`_persist_dispatch`, `_persist_completion`, `_initialize_schema`, `recover_abandoned_delegations`, `restore_undelivered_completions`, `sweep_orphaned_completions`, claim/release/defer/drop/complete delivery functions, `claim_completion_delivery`).
- `agent/delegation_provider.py` (117 lines): "A delegation provider decides HOW one `delegate_task` task becomes a child run: which model, which credentials, which tools, which terminal policy, and what extra schema the task carries." Backends are plugins registered via `PluginContext.register_delegation_provider`; selection is `delegation.backend` in config, default `"default"`. A missing/disabled/unavailable backend **fails closed** (tool error naming it, never a silent run on another route).
- `agent/delegation_registry.py` (135 lines): the registry; the bundled `plugins/delegation/default/` (38-line `__init__.py`, 5-line `plugin.yaml`) is "itself a plugin, registered through the same seam as any other" (module docstring).
- `agent/delegation_backends.py` (157 lines): `BackendInfo`, `list_backends`, `saved_backend`, `set_global_backend`, `/delegation` command support. `agent/delegation_context.py` (187 lines) and `agent/delegation_provider.py` carry the per-task context/routing.
- **Advanced-delegation plugin is NOT installed:** `plugin-catalog/advanced-delegation.yaml` exists, but there is no `advanced-delegation` directory under `plugins/`. The config examples that reference its `model_map` backend (named `fast`/`deep` routes with per-route provider/model/reasoning_effort/service_tier/fallback_providers) and its `profile_routes` backend (a listed profile's subagents use *its* credentials, pool, `SOUL.md` and terminal policy) are therefore **not live in this tree** — they are catalog documentation. The closest live equivalent is the flat `delegation.model` / `delegation.provider` override (§3, limits).

### Child lifecycle
- `agent/subagent_lifecycle.py` (470 lines): `SubagentState` enum — `PENDING, STARTING, RUNNING, SUCCEEDED, FAILED, INTERRUPTED, CANCEL_REQUESTED, CANCELLED, UNKNOWN`; `SubagentLaunchRequest` (`goal`, …), `SubagentHandle`, `SubagentStatus`, `SubagentTerminalState`, `SubagentResult`, `SubagentCancelResult`, `SubagentReconnectResult`; `SubagentLifecycleService` with `launch / status / wait / cancel / result / reconnect / steer`. Children are real `AIAgent` instances in-process (or via `agent/managed_worker.py` frame protocol, `agent/runtime_session_child.py`, `agent/process_bootstrap.py`).
- `hermes_state_delegate_children.py`: a single function, `delegate_descendant_ids(db, session_id)` — the state layer tracks parent→child lineage and little else.
- `tools/async_delegation.py` fan-out: one `delegate_task` call can dispatch a batch or a `group` of units as one agent; `evals/delegation_grouping/` is an A/B harness for result delivery (see below), not a team feature.

### Limits (all from live config/code)
- Config `delegation:` (`config.yaml:1912-1964`): `max_iterations: 250` per child (live); `max_concurrent_children: 10` (commented, default 10, floor 1, no ceiling — "values above 10 multiply API cost linearly"); `max_spawn_depth: 1` (commented, range 1–3, default 1 = flat; depth 2 requires `role="orchestrator"` on intermediates); `orchestrator_enabled: true` (commented kill-switch); `subagent_auto_approve: false` (commented — a child hitting a dangerous-command prompt auto-denies; the parent TUI owns stdin so blocking would deadlock); `inherit_mcp_toolsets: true` (commented); `model` / `provider` override for children (commented — "Resolves full credentials (base_url, api_key) automatically. Supported: openrouter, nous, zai, kimi-coding, minimax"); `fallback_providers` chain for children (commented).
- Result delivery: `evals/delegation_grouping/README.md` — "Does a parent that will answer only after every subagent finishes get the results in ONE message, and does a parent that must act on each result as it lands still get them one at a time? Run with `delegation.independent_completions: true`, the only configuration where the model makes that choice." Scoring is runtime accounting (completion units delivered, parent turns after dispatch, task success by oracle, summed parent+child tokens). This is a **delivery-batching experiment**, not persistent grouping.
- Shared context: children get a task-scoped context bundle (`delegation_context.py`) and return results to the parent turn; there is no shared blackboard, no child-to-child messaging, no persistent child memory across tasks, and no child identity that survives its task. `agent/side_question.py` (+ lease/request) is a lighter-weight ask-a-side-agent path, also ephemeral.
- `agent/curator.py`, `agent/review_engine.py`, `agent/background_review.py` — post-hoc review of work, not a team member role.

### `plugins/teams_pipeline` — NOT agent teams (name trap)
- `plugins/teams_pipeline/` (`cli.py` 316, `pipeline.py` 498, `meetings.py` 250, `models.py` 215, `runtime.py` 110, `store.py` 116, `subscriptions.py` 122, `plugin.yaml` 38 lines): "Microsoft Teams meeting pipeline plugin with durable runtime state and operator CLI flows for Graph-backed transcript-first meeting summaries." It is a **Microsoft Teams meeting-transcript pipeline**. It has nothing to do with multi-agent teams and must not be cited as team infrastructure.

### The closest thing to a team: hosted rooms (gateway)
- `gateway/hosted_rooms.py` + ~25 `gateway/hosted_room_*.py` files (7,971 lines total): durable multi-member rooms spanning gateways, with members, authority/grants, work records/storage/lineage, router, lead, driver, discussion policy.
- `gateway/hosted_room_discussion.py`: "Deterministic policy for same-gateway hosted-room Discussions. Pure (no I/O, transport or model knowledge): a frozen local roster plus the complete typed room log yields at most one next driver task." Constants: `MAX_DISCUSSION_MEMBERS = 6`, `MIN_DISCUSSION_MEMBERS = 2`, `MAX_DISCUSSION_ROUNDS = 3`, `MAX_DISCUSSION_MESSAGES = 10`. Config `hosted_rooms.discussion: {max_rounds: 3, max_messages: 10}` (`config.yaml:1091`); `group_sessions_per_user: true` (line 1078). Cross-gateway rooms use `gateway.room_link_url` (commented; "Set this only to the public HTTPS base URL that another trusted Hermes gateway can reach… Network access should still be limited to the peer gateways").
- What it is: a **bounded discussion protocol between Hermes instances/gateways** (members reply, a driver task is derived deterministically, terminal events settle), with durable typed logs so a restart reconstructs tasks. What it is not: members are gateway peers, not named persistent team members with roles, pinned models, or a team brain; rounds/messages are hard-capped (3/10); there is no shared long-term team memory, no task board, no role assignment, no Main Brain that owns the goal across sessions.
- Related: `gateway/session_group_controls.py`, `gateway/session_group_peers.py`, `gateway/session_bot.py`, `gateway/session_moa_turn.py`, `gateway/session_worker*.py` (worker spawn/reservation), `agent/managed_worker.py`.

### Verdict on "team" in Hermes today
Hermes has **ephemeral fan-out** (one parent, N short-lived children, flat by default, results funneled back into the parent's turn) plus a **bounded multi-gateway discussion room**. It has no persistent team: no roster, no member identity/pinned model/credentials per member, no inter-member channel, no team memory, no team brain, no goal ownership that outlives a turn. That is the core gap Airlangga must build — it cannot be assembled from `delegate_task` flags alone.

## 6. What to KEEP, REPLACE, DROP for Airlangga

Airlangga target (from the order): Agentic Team — distinct from Swarm/subagent/orchestrator-AI — with a Main Brain and Group/Team Brains, and per-member multi-AI configuration (any vendor, official API or custom `base_url`).

### KEEP (use as-is, do not rebuild)
- **Provider profile system** (`providers/base.py` + `plugins/model-providers/*`): declarative `ProviderProfile` with `base_url`, `api_mode` auto-detection, per-provider headers/reasoning vocab. 39 providers already cover OpenAI-compatible, Anthropic-native, Codex Responses, Gemini, Bedrock, Vertex, Azure. Airlangga's per-member provider config is a *roster entry pointing at a profile*, not a new provider system.
- **Custom-provider path** (`custom` provider + named `providers:` entries with `base_url`/`key_env`/`key_cmd`/`extra_headers`/`extra_body`): already answers "any AI from anywhere, official API or custom base_url". Keep the semantics; add per-member binding.
- **Credential pool + fallback chains** (`agent/credential_pool*.py`): rotation, cooldowns, per-model fallback. Keep, but scope pools per member (today they are per session/global).
- **Turn engine + tool executor + compaction** (`agent/conversation_loop.py`, `turn_facade.py`, `tool_executor.py`, `context_compressor*.py`): a proven single-agent loop. Each Team Brain / member runs one of these; do not rewrite the loop.
- **Toolsets + skills surfaces** (`toolsets.py`, `skills/`, `optional-skills/`): composition by platform/role already exists. Keep; add per-member toolset/skill scoping (today scoping is per platform, not per member).
- **State DB + `hermes_state_*` modularisation**: the 67-module split is the right pattern for adding `team_*` state modules (roster, member sessions, team memory, decision log) without touching the session core.
- **Cron scheduler** (`cron/scheduler.py`, 60s tick, file lock, per-job model pin): keep; team-scheduled work is a cron job with a team target.
- **Guardrail layers 1–5 and 8** (approval floors/detection, file safety, skills guard, tool guardrails, runtime self-protection, redaction/SSRF): keep all. They are the reason Hermes can be trusted to run tools at all. **Decision needed:** approvals mode is currently `off` on this VPS — Airlangga must pick a mode deliberately (`smart` for team members that run tools; `off` only on a disposable host), not inherit `off` by accident.
- **API-server `model_routes`** (`platforms.api_server.extra.model_routes`): keep as the external multi-model front door; Airlangga can expose team members as routes.
- **Hosted-room durable log pattern** (`gateway/hosted_rooms*.py`): keep the *pattern* (typed immutable events, deterministic reconstruction after restart, authority/grants) for the team decision log — but not the 3-round/10-message discussion limits.

### REPLACE (Hermes has a related mechanism, but it answers a different question)
- **Delegation → Team runtime.** `delegate_task` + `SubagentLifecycleService` + `async_delegation.py` give ephemeral, flat, parent-owned children. Replace with: persistent `Team` (roster of named members, each with pinned provider/model/credentials/toolsets/role/SOUL), `TeamBrain` (owns the goal across turns/sessions, holds team memory and the decision log), `MainBrain` (the user-facing brain that decomposes goals, assigns work, and synthesises — it does *not* do member work itself). Member lifecycle needs states beyond `PENDING…CANCELLED`: `IDLE / WORKING / BLOCKED / REVIEWING / DONE`, plus steering, handoff, and replacement of a failed member. The `SubagentState` enum and `launch/status/wait/cancel/result/reconnect/steer` service shape are a good template — extend, don't copy-paste.
- **Result delivery → Team blackboard.** The `async_delegation.py` SQLite completion queue + `delegation_grouping` one-vs-batched delivery is parent-turn-scoped. Replace with a durable team blackboard (shared context, artefacts, claims, open questions) that all members read/write and that survives the parent turn. The queue's claim/release/delivery semantics are reusable inside it.
- **`model_map` / `profile_routes` (catalog-only) → real per-member routing.** The advanced-delegation plugin is not installed; its config examples are the spec to implement: named routes with provider/model/reasoning/service_tier/fallback, and profiles whose members use *their own* credentials, pool, SOUL.md and terminal policy. Implement as first-class config (`teams.<name>.members[].provider/model/base_url/api_key_ref/reasoning/toolsets`), not a plugin.
- **MoA → Team deliberation.** `moa_loop.py` (one-turn, reference-model consultation, loop still owns tools) becomes the *deliberation primitive*: a Team Brain can run a MoA round across member models for a contested decision, with the trace (`moa_trace.py`) stored in the team decision log. Keep the code; change the caller from "one turn" to "team decision".
- **Hosted-room discussion → Team meeting protocol.** Keep the deterministic-log pattern; replace the caps (6 members / 3 rounds / 10 messages) with a goal-driven protocol (propose → critique → vote/settle, terminal states `settled/failed/cancelled/deferred` already exist as `TerminalKind`), and replace gateway-peer members with roster members.
- **Single-brain system prompt → layered prompts.** `prompt_builder.py` / `system_prompt.py` assemble one brain's prompt. Airlangga needs three layers: Main Brain (goal, delegation policy, synthesis rules), Team Brain (team goal, member roster, shared context), Member (role, tools, output contract). Shared context must be assembled per layer, not inherited wholesale from the parent.
- **Memory → team memory.** `MemoryManager` is per-agent and char-capped (2,200/1,375). Add a team-level memory provider (shared facts, decisions, conventions) with per-member private memory kept separate. The memory-provider plugin interface (`agent/memory_provider.py`, `agent/agent_init_memory_provider.py`) is the seam to implement against.

### DROP (do not carry into Airlangga)
- **`plugins/teams_pipeline`** — Microsoft Teams meeting summaries; the name is a trap, the function is irrelevant. Drop entirely.
- **The 12,005-file monolith shape.** Do not fork the whole tree. Airlangga should be a new, small core (team runtime + roster/config + blackboard + layered prompts + per-member provider binding) that *imports* Hermes' provider/turn/tool/state libraries — or, if a fork is unavoidable, vendor only `providers/`, `agent/` (turn/tool/compaction/memory), `tools/` (approval + delegation queue), `hermes_state*.py`, `cron/` and `gateway/platforms/api_server.py`. `apps/` (63M), `hermes_cli/` (29M TUI/desktop), `evals/` (3.0M), `website/` and the messaging-platform adapters are not needed for a team core.
- **Single global `model:` default as the only model.** The config's one `model.default` + one `provider: auto` is the wrong shape for a team; it becomes the Main Brain's default only, with members overriding per roster entry.
- **`max_spawn_depth: 1` flat default and the orchestrator kill-switch as the only hierarchy.** A team is a hierarchy by design (Main → Team → Member); depth limits become a team-topology concern, not a global cap.
- **Approval `mode: off` as an inherited default.** Do not carry the current VPS config's `off`/`approve`/`approve`/`false` into Airlangga. Default to `smart` for any member with tool access; `off` only behind an explicit, disposable-host flag.
- **Gateway messaging-platform surface** (Telegram/Discord/WhatsApp/…) for v1: a team does not need nine chat adapters. Keep only the API server (and optionally CLI) as the control surface until the team runtime is proven.
- **`evals/delegation_grouping` battery as a team metric.** It measures parent-turn delivery batching; team success needs different metrics (goal completion, member utilisation, cost per goal, decision quality, rework rate). Keep the oracle-scoring idea, drop the battery.

### Gaps Hermes does not cover at all (new build, no reuse)
1. Team roster/config schema + validation (member identity, role, provider/model/base_url/key ref, toolsets, SOUL, terminal policy, budget).
2. Main Brain ↔ Team Brain protocol (goal decomposition, assignment, progress, escalation, synthesis, conflict resolution).
3. Persistent team memory + decision log + blackboard (durable, restart-safe, restart-reconstructable like hosted rooms, but goal-scoped).
4. Member-to-member communication (today children cannot talk to each other; all traffic goes through the parent turn).
5. Cost accounting per member/per goal (usage exists per session — `agent/usage_*.py`, `hermes_state_usage.py`, `agent/account_usage*.py` — but not aggregated per team/goal).
6. Team-level guardrails: per-member approval policy (a researcher member may be read-only while a coder member needs `smart`), per-member budget caps, cross-member secret isolation (one member's credentials must not leak into another member's context).

### Suggested Airlangga skeleton (from this teardown, not from Hermes)
- `airlangga/team.py` — roster, topology (Main → Teams → Members), lifecycle states.
- `airlangga/brain.py` — Main Brain and Team Brain as thin wrappers over one `AIAgent` each, with layered prompts.
- `airlangga/member.py` — member runtime: one `AIAgent` + pinned `ProviderProfile` + credential-pool scope + toolset/skill scope.
- `airlangga/blackboard.py` — durable shared context (reuse `async_delegation.py` queue semantics + hosted-room typed-event log pattern).
- `airlangga/memory.py` — team memory provider implementing the `memory_provider` plugin interface.
- `airlangga/router.py` — per-member provider/model resolution (generalise `model_routes` + `model_map` config examples into roster entries).
- `airlangga/guardrails.py` — per-member approval/budget/secret policy layered on top of Hermes layers 1–5 (not instead of them).
- Config: `airlangga.yaml` (teams, members, brains) kept separate from `config.yaml`; Hermes `config.yaml` remains the provider/tool/cron source of truth.
